# Deep-research prompt: speed + memory options for Ornith-1.5-35B-A3B on Swiftlet

## Task

I run a 35B-parameter mixture-of-experts (MoE) language model locally on Apple Silicon through a custom Swift/Metal inference engine. I've already done a first round of profiling-driven optimization (details below) and want you to research **further options to increase decode throughput (tokens/sec) and/or reduce memory footprint**, specifically ones I haven't already tried or already ruled out. Prioritize recent (last ~18 months), concrete, implementable techniques over generic advice. For each option, tell me: what it is, the mechanism by which it helps, roughly how much it tends to help in practice (with sources), how hard it would be to implement in a from-scratch Swift/Metal engine (not PyTorch/llama.cpp — I can't just `pip install` someone else's kernel), and what it would cost in complexity/correctness risk. Cite your sources (papers, blog posts, GitHub issues/PRs, benchmark write-ups) so I can verify claims myself.

## System context

- **Model**: a hybrid GatedDeltaNet (linear attention) + MoE architecture (Qwen3.5-MoE family), ~35B total parameters, ~3B active per token ("A3B"). 40 layers; every 4th layer is full (GQA) attention, the other 30 are linear attention (GatedDeltaNet: 16 key-heads/32 value-heads, head dim 128, conv kernel 4). Full-attention layers: 16 query heads, 2 KV heads, head dim 256. 256 routed experts, top-8 routing per token, MoE intermediate size 512, plus one shared expert (intermediate size 512 too). Hidden size 2048, vocab 248,320.
- **Quantization**: 4-bit affine, group size 64 (MLX's quant scheme). Weights live in a custom container format ("qpack"): small resident dense weights (~1.3 GiB) stay in memory; the 256×40 = 10,240 routed-expert weight blocks stream from local SSD on demand through a bounded, budget-configurable expert cache (min-heap LFU+recency eviction), not memory-mapped wholesale — conceptually similar to MoE weight offloading (à la DeepSpeed-MoE, FlexGen, AirLLM, or llama.cpp's approach), but a fully custom implementation.
- **Hardware target**: Apple Silicon (tested on an M3 Pro, 18 GB unified memory), Metal compute, no discrete GPU, no cloud/network offload allowed — everything must run fully local and fully offline.
- **Runtime today**: `--cache-gb 2` (expert-cache budget) is the current default/sweet spot; ~55-60% cache hit rate at that budget. Decode throughput ~9.9-11.1 tok/s depending on context length reached (grows with context because of one specific cost — see below). At 32K context: ~1.3 GiB resident dense weights + ~63 MiB fixed linear-attention recurrent state + ~1.25 GiB KV cache (FP32, full-attention layers only) + 256 MiB scratch + 8% safety margin ≈ 3.1 GiB floor; anything above that is expert-cache budget (e.g. 4 GiB target → ~500 resident expert slots; 8 GiB target → ~2,733 slots, of 10,240 total).
- **Constraints**: implementation must be plain Swift + Metal (Metal shading language for kernels, Accelerate/vDSP/BLAS for CPU-side vector math) — no PyTorch/ONNX/llama.cpp runtime dependency, no server-side/cloud component, no retraining or fine-tuning of the model. Any correctness-changing technique must be independently verifiable (byte-identical or measurably-bounded-difference output vs. a known-good baseline) — this project's own convention is to verify every change this rigorously before shipping it, not trust benchmarks alone.

## What's already been done (verified, shipped) — don't re-suggest these as new ideas

Decode throughput arc so far: **5.79 → ~9.9-11.1 tok/s** (same reference prompt/qpack, `--cache-gb 2`), via:

1. **Bounded concurrent expert-cache fill**: was strictly serial `pread` per cache miss (GPU fully idle during fill, ~46% of decode wall). Switched to bounded concurrent reads (width 4-8) within a layer's top-K miss batch. ~56% throughput win alone.
2. **Fixed a measurement bug** (prefill's cache stats had been folded into decode's) + **replaced an O(slots) linear-scan LFU eviction victim search with a min-heap** (bookkeeping cost 1.30s → 0.12s per run).
3. **MoE kernel fusion**: a new bindless batched-GEMV Metal kernel collapsed up to 38 separate GPU dispatches per MoE layer (per-expert gate/up/silu_mul/down loops) down to 9 (one dispatch per stage across all K resident experts via each expert's raw GPU buffer address). +5-6% — smaller than the ~2x dispatch-count reduction suggested, because most of decode's GPU time turned out to be real memory-bandwidth-bound compute, not per-dispatch fixed overhead.
4. **Vectorized the CPU-side full-attention core** (`cblas_sgemv`/vDSP replacing hand-written scalar Swift loops for QK^T and the softmax-weighted V-sum, plus rmsNorm/softmax). This is the one decode-time cost in the whole pipeline that's O(context length) rather than O(1) — everything else here is flat per-step cost. +4.3% at 200 tokens, +11.4% at 354 tokens (grows with context, as predicted).
5. A recent fix to a **repetition-guard sampling bug** unrelated to raw throughput (was corrupting long code-generation output) — not a perf item, mentioned only for completeness.

## Investigated and explicitly rejected, with real A/B evidence — don't re-suggest without a genuinely new angle

1. **Raising `--cache-gb` above 2.** Hit rate climbs a lot (60%→90%, misses 28,093→7,060) but decode wall barely moves (22.9s→21.9s). A "GPU wait-minus-real-exec" gap grows alongside the larger resident-buffer set (2.76s at 1,213 slots → 4.83s at 4,854 slots), offsetting the fill-time savings almost exactly.
2. **Metal `.hazardTrackingModeUntracked` for expert-cache slot buffers**, hypothesized as the cause of that gap (every other persistent buffer in the pipeline already uses untracked mode; expert-cache slots didn't). Tested directly, same binary, A/B across `--cache-gb` 2/4/6/8: rejected — the gap didn't shrink, and was sometimes slightly *worse* at the largest cache size, replicated across a repeat run. Leading remaining (untested) theory: real memory pressure / page-in on the 18 GB unified-memory machine, not resource-tracking overhead — nobody has instrumented `vm_stat`/working-set during a run yet to confirm this.
3. **Overlapping expert-cache fill with GPU MoE dispatch further.** The real decode path already defers layer N's MoE compute into layer N+1's command buffer (genuine pipelining already in place — a router GEMV inside layer N's own command buffer must complete before that layer's fill can start, a true data dependency, not just scheduling). The one remaining independent piece (the shared expert's GEMV chain) is only ~1/8 the routed-experts' per-layer GPU cost, estimated to hide only 1-2% of decode wall — not worth the risk of restructuring a barrier-synchronized, register-offset Metal kernel pipeline for that return.
4. **MTP speculative decoding** using this checkpoint's own (currently-dropped) one-layer speculative head. Architecturally plausible but blocked on two things: (a) this codebase has no autoregressive multi-token speculative decode loop yet, (b) an unresolved question of how to correctly roll back GatedDeltaNet's recurrent linear-attention state on a rejected speculative token — trivial for a standard KV cache (just truncate), unclear for a fused recurrent state.
5. **DFlash-style diffusion-drafter speculative decoding.** Needs a trained drafter model that doesn't exist for this checkpoint; not pursued (no training infrastructure, no compute budget for training one).

## What I want you to research (this is the actual ask)

1. **Speculative/parallel decoding for hybrid linear-attention+MoE architectures specifically.** Standard speculative decoding (Medusa, EAGLE, lookahead decoding, self-speculative decoding, prompt lookup decoding, etc.) is well-documented for plain transformers with a standard KV cache — but this model's recurrent GatedDeltaNet state doesn't roll back the way a KV cache does. Is there published work (papers, blog posts, GitHub discussions) specifically on speculative decoding for Mamba/SSM/GatedDeltaNet/Jamba-style hybrid architectures, or on how other projects have solved (or avoided) the "rejected draft token needs recurrent-state rollback" problem? Concretely: is checkpointing/restoring the small fixed-size recurrent state (tens of MiB, per the memory numbers above) before each speculative window a viable, cheap answer, or is there a smarter approach in the literature?
2. **Better/cheaper quantization for the expert weights**, beyond 4-bit affine group-64. Newer schemes (e.g. lower-bit with outlier handling, mixed-precision per-tensor or per-expert, calibration-based methods like GPTQ/AWQ if the quantization step were redone) — what's the realistic quality/size/speed tradeoff for going further, and is any of it feasible to implement as a Metal dequantize kernel without a full retrain/recalibration pipeline?
3. **KV cache compression for the full-attention layers**, which are currently stored uncompressed (FP32). Only 10 of 40 layers need this (the rest are linear-attention with fixed-size state, not growing KV). Int8/int4 KV cache quantization, windowed/sliding-window attention, or other cache-shrinking techniques that have documented quality-preserving results — and whether any generalize easily to a hand-rolled Metal implementation.
4. **Smarter expert-cache eviction/prefetching** beyond LFU+recency. Is there research or production systems (vLLM, DeepSpeed-MoE, FlexGen, AirLLM, Mixtral offloading projects, etc.) doing router-pattern-aware prefetching for MoE — e.g., predicting layer N+1's likely-active experts from layer N's hidden state or router logits before layer N's own compute finishes, to start disk reads earlier than a purely reactive miss-driven cache allows?
5. **Faster local SSD read path on macOS/Apple Silicon** for the expert-cache miss-fill specifically. Is bounded-concurrency `pread` actually close to optimal on Apple's NVMe/unified-memory-storage stack, or are there known-better patterns (io_uring-equivalent APIs, `F_NOCACHE`/`F_RDADVISE`, mmap+`madvise` hints, larger/aligned read sizes, avoiding double-buffering) worth trying?
6. **Continuous/concurrent request batching.** The current server handles one request at a time (shared mutable conversation state). Is there a well-understood, memory-bounded way to serve multiple concurrent requests against a single resident expert cache for a MoE model specifically (shared cache benefits vs. per-request KV/state memory cost), and what do systems like vLLM/TGI/SGLang do differently for MoE vs. dense models here?
7. **Prompt/prefix caching across independent requests** at the server layer (today, only same-conversation continuations reuse state; a fresh conversation always reprocesses its full prompt). Worth it for typical agentic/tool-calling workloads with repeated system prompts?
8. **Offline expert pruning or merging** for an already-trained, already-quantized MoE checkpoint (given only 8 of 256 experts activate per token) — is there credible published work on shrinking the *total* expert pool post-hoc (to cut disk footprint and raise cache hit rate) without a full retrain, and what quality cost does it typically carry?
9. **Anything Apple-Silicon-specific I'm not using**: Apple Neural Engine (ANE) offload feasibility for any part of this pipeline (given it's Metal/GPU-only today and ANE access from a non-CoreML custom kernel pipeline is famously restricted), Metal Performance Shaders Graph vs. hand-written kernels, or unified-memory-specific tuning (page size, `MTLResourceOptions`, `MTLHeap` usage) relevant to a workload like this.
